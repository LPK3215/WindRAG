# 2. 核心数据流

分三段：**离线索引构建** → **在线查询检索** → **答案生成**。所有路径均落到文件与函数。

---

## 2.1 离线索引构建链路

触发：`python src/build_index.py`

```
DataProcessor.load_all_data()              data_processing.py:33
  ├─ load_fault_cases()      fault_cases.json
  ├─ load_technical_docs()   technical_docs.json
  └─ load_operations_manual() operations_manual.json
        │
        ▼
DataProcessor.process_all()                data_processing.py:107
  └─ process_documents()  → split_into_chunks()   data_processing.py:125 / 175
        │  切分策略(关键):
        │   • 按句号/换行切句，每chunk 1~3句 (data_processing.py:175-224)
        │   • 长句截断 MAX_CHUNK_LENGTH=500; 短chunk(<50字)并入前块
        │   • 每个chunk带 metadata: source/component/category/type
        ▼
IndexBuilder(embeddings, bm25)             build_index.py:11
  ├─ build_vector_index(): model.encode(chunks) → FAISS(InnerProduct)  build_index.py:24
  ├─ build_bm25_index(): BM25Okapi(tokenized)                    build_index.py:55
  ├─ save_index(): 持久化 embeddings.npy / faiss_index / bm25.pkl / chunks.json  build_index.py:64
  ▼
KnowledgeGraph.construct_knowledge_graph()  knowledge_graph.py:11
  └─ 从 fault_cases/technical_docs 抽取三元组 → NetworkX 图 → 落盘 data/knowledge_graph.json
      (run_rag.py:131 load_or_build 在初始化时调用)
```

**注意**：KG 的 `construct_knowledge_graph` 在 `WindTurbineRAG.__init__` 内被 `load_or_build` 触发（run_rag.py:131），并非由 `build_index.py` 调用——两路构建**各自独立**，KG 不参与 `build_index.py` 的 FAISS/BM25 产物。

## 2.2 在线查询检索链路

触发：`rag.query(question, top_k)`（run_rag.py:322）

```
query()
  ├─ 向量检索   vector_retrieve(query, k*2)        run_rag.py:182
  │     • self.model.encode([query]) → cosine / faiss.search
  │     • 返回 (doc, score) 列表
  ├─ BM25检索  bm25_retrieve(query, k*2)           run_rag.py:196
  │     • tokenize → self.bm25.get_scores() → 排序
  ├─ KG检索    kg_retrieve(query, k)               run_rag.py:210
  │     • kg.semantic_query(query, model, k)  (knowledge_graph.py:187)
  │     • 对 query 与每个节点 description 做 embedding 余弦相似度
  ├─ 自适应α   adaptive_fusion.predict_alpha()     run_rag.py:164 (若 adaptive_fusion_loaded)
  │     • 否则固定 α=0.7
  ├─ 融合       score = α·vec + (1-α)·bm25          run_rag.py:228
  │     • 按 content 合并去重，KG 结果直接附加(不参与α加权)
  └─ 重排       _rerank_documents(query, docs, k)   run_rag.py:242
        • 用 query 与每个 doc 的 embedding 余弦相似度重排 top-k
```

**关键细节**：
- `retrieve_documents` 各路取 `k*2` 候选，融合后若 `use_rerank` 则对 top-k 做余弦重排（run_rag.py:241-242）。
- KG 文档 `source='knowledge_graph'`，在融合阶段**直接 append**，不乘 α（run_rag.py:210-214 与融合循环 228-238 分开处理）。

## 2.3 答案生成链路

```
generate_answer(query, docs)                run_rag.py:322
  ├─ 格式化上下文 _format_context(docs)     run_rag.py:360
  │     • 拼接 content + 来源 + 部件 + 类别
  ├─ 有LLM且 enabled:
  │     model_manager.get_response(prompt)   run_rag.py:344
  │       └─ 遍历模型 → _call_model() → 成功返回; 失败 try_next()
  └─ 无LLM / 全部失败:
        _generate_template_answer()          run_rag.py:370
          • 基于 component 命中预定义模板库（叶片/齿轮箱/轴承…）
          • 命中则返回结构化处理建议; 否则返回通用提示
```

**降级链**：LLM 配置缺失 → 模板；LLM 调用抛错 → 模型池切换下一个 → 全部失败 → 模板（run_rag.py:344-356, 370）。

---

## 2.4 数据流中的"可追溯性"现状

- ✅ 每个 retrieved doc 都带 `metadata.source/component/category`（切分时写入，data_processing.py）。
- ✅ Gradio 界面把来源/部件/评分以表格展示（gradio_app.py:61-67），KG 命中单独标出（gradio_app.py:70-74）。
- ❌ **答案本身不内联引用标记**（如 `[1]` 角标），仅把文档列表附在侧栏——属于"弱可追溯"，非端到端引用回链。
