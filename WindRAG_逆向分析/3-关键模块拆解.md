# 3. 关键模块拆解

挑 5 个最核心模块，按"做什么 / 怎么做 / 为什么"拆解。

---

## 3.1 `run_rag.py` · `WindTurbineRAG`（系统门面）

- **做什么**：整个 RAG 系统的统一入口与编排者。聚合嵌入模型、向量/BM25/KG 三路检索、自适应融合、LLM 模型池；对外暴露 `query()` 与 `retrieve_documents()`。
- **怎么做**：
  - `__init__`（run_rag.py:104-169）：先用 `load_dotenv` 读 `config.env`（run_rag.py:105-108）；加载 SentenceTransformer `text2vec-base-chinese`（run_rag.py:118）；`IndexBuilder.load_index()` 恢复向量+BM25（run_rag.py:143-144）；`KnowledgeGraph.load_or_build()` 恢复/构建图谱（run_rag.py:131）；`LLMModelManager` 初始化（run_rag.py:152）；自适应模型按需加载（run_rag.py:156-162，`adaptive_fusion_loaded` 标志位）。
  - `query()`（run_rag.py:322）：检索→生成两段式。
  - `retrieve_documents()`（run_rag.py:216）：三路检索→融合→重排。
- **为什么这么做**：用 Facade 把 6 个子模块收敛到一个类，入口层（CLI/Web）只需 `from run_rag import WindTurbineRAG`，极大降低调用方复杂度。这是原型阶段正确的工程取舍。

## 3.2 `adaptive_fusion.py` · `AdaptiveFusionModel`（自适应融合核心创新点）

- **做什么**：给定查询，预测向量检索与 BM25 的融合权重 α∈[0,1]。α→0 偏 BM25（精确术语/编号），α→1 偏向量（口语语义）。
- **怎么做**（`predict_alpha`，adaptive_fusion.py:65-99）：
  1. 用 `query_features.py` 抽取 16 维特征（关键词数、数字数、标准号命中、平均词长等）。
  2. `scaler.transform(features)` 标准化 → MLP `model.predict()` 得残差 `residual`。
  3. **规则先验** `rule_based_alpha(features)`（adaptive_fusion.py:101-135）：含标准号/多数字→α 压低（偏BM25）；长查询/多领域词→α 抬高。
  4. **最终 α = clip(rule_based_alpha + residual, 0.1, 0.95)**（adaptive_fusion.py:97-99）。
- **为什么这么做**（设计亮点）：
  - 纯 MLP 在小样本下易过拟合/不可解释；作者用「**可解释规则先验 + 轻量 MLP 学残差**」的混合结构，兼顾可解释性与微调能力。这正是该仓库区别于普通 RAG 的核心创新。
  - 残差用 `tanh` 激活（adaptive_fusion.py:54）限制范围，避免 MLP 把 α 推飞。
- **训练样本来源**：`generate_training_data.py` 用 `DomainConfig` 的领域词人工合成"含标准号→低α / 口语→高α"的正负样本（generate_training_data.py:171-197），`train_adaptive_fusion.py` 用 `MLPRegressor` 训练。⚠️ 待核实：样本为合成标签，真实泛化性未与人工标注对比验证（ablation 仅用关键词覆盖率间接证明）。

## 3.3 `knowledge_graph.py` · `KnowledgeGraph`（第三路检索）

- **做什么**：把风电故障案例/技术文档的结构化信息建成 NetworkX 图，提供"语义查询"作为第三路召回。
- **怎么做**：
  - `construct_knowledge_graph()`（knowledge_graph.py:11-160）：遍历 fault_cases 建 `(component)-(fault_type)` 边、technical_docs 建 `(component)-(category)` 边；节点带 `description`（聚合 component/fault_type 文本）。
  - `semantic_query()`（knowledge_graph.py:187-234）：对 query 与每个节点 description 做 embedding 余弦，取 top-k 节点，把其 description 作为 KG "文档"返回（source='knowledge_graph'）。
  - `get_node_info()`（knowledge_graph.py:236-270）：返回某节点的邻居/边，供答案生成补充。
- **为什么这么做**：传统 RAG 缺"实体关系"召回，KG 补上结构化知识。但本实现的"语义查询"本质仍是**节点 description 的向量召回**，并非图遍历推理（无 multi-hop、无关系路径推理）。属"轻量图谱增强"，非真正 graph-RAG。

## 3.4 `model_manager.py` · `LLMModelManager`（鲁棒生成层）

- **做什么**：管理多个 ModelScope LLM（Qwen 系列），线程安全地生成回答，并在单模型失败时自动切换、最终降级。
- **怎么做**：
  - `__init__`（model_manager.py:15-67）：从 `MODELSCOPE_API_KEY` 读 key，构建模型列表（默认 Qwen-Plus 等，model_manager.py:27-33），`self.lock = threading.Lock()`。
  - `get_response()`（model_manager.py:77-116）：遍历 `self.models`，`with self.lock` 调 `_call_model()`（model_manager.py:121-135，即用 `openai.OpenAI` 兼容客户端发 chat completion）；成功即返回，抛错则 `print` 警告并 `try_next`，全失败返回 `None`。
  - 调用方 `run_rag` 在 `None` 或 `use_llm=False` 时走 `_generate_template_answer`（run_rag.py:370）。
- **为什么这么做**：
  - **线程安全 + 优雅降级**是该模块最大价值：Gradio 多用户并发时 `Lock` 防止共享客户端状态错乱；模型不可用不崩系统，回退到模板——保证"永远有答案"。
  - 局限：降级是"穷举式"而非"按错误类型路由"（限流/超时/鉴权错混为一谈），无退避重试。

## 3.5 `data_processing.py` · `DataProcessor`（数据接入与切分）

- **做什么**：加载 3 类合成 JSON 数据源，统一切成带 metadata 的 chunk，供建索引。
- **怎么做**：
  - `load_all_data()`（data_processing.py:33-105）：分别读 fault_cases/technical_docs/operations_manual，标准化为 `{content, metadata}`。
  - `split_into_chunks()`（data_processing.py:175-224）：按句切分，1~3 句/块；长句截断 500 字；短块(<50字)合并前块。
  - 每 chunk metadata 含 `source/component/category/type`。
- **为什么这么做**：句级 chunk 保证语义完整、避免跨主题断裂；metadata 携带组件/类别，是后续"可追溯 + 模板答案按 component 路由"的基础。
- **局限**：无重叠滑窗（overlap），可能切断跨句指代；无表格/层级结构保留（对运维手册中的参数表不友好）。
